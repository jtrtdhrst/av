## Co zmieniono

- `mcp/public/.htaccess`: `Referrer-Policy: no-referrer` → `strict-origin-when-cross-origin`.
- `app/Auth.php`: `requireSameOrigin(bool $allowNullOrigin = false)` — opcjonalna akceptacja dosłownego `Origin: null` dla endpointów z własnym tokenem CSRF.
- `app/Mcp/Http/OAuthController.php`: `POST /oauth/connected/revoke` woła `requireSameOrigin(true)`.
- `tests/mcp-login.e2e.mjs`: krok 8 — `GET /oauth/connected`, unieważnienie z `Origin: null`, obcy `Origin` i zły CSRF bez efektu, token unieważniony, drugi klient zachowuje dostęp.
- Dokumentacja: `DOCUMENTATION.md` (§14.6, tabela bezpieczeństwa), `docs/MCP.md`, `docs/TESTOWANIE.md`, `CHANGELOG.md` 3.9.8 + `public/docs` z generatora.

Punkt styku: P14 (MCP OAuth/consent) — bez zmian w API danych i schemacie.

## Dlaczego

Unieważnianie dostępu na `https://mcp.alphavault.pl/oauth/connected` zwracało:

```json
{"error":"bad_origin","message":"Nieprawidłowe źródło żądania.","origin":"null","path":"/oauth/connected/revoke"}
```

Host MCP wysyłał `Referrer-Policy: no-referrer`; Chromium i Firefox zerują wtedy `Origin` formularzy `POST` (wysyłają dosłowne `null`). `requireSameOrigin()` traktował to jak obce pochodzenie i blokował jedyną ścieżkę odebrania tokenu, więc użytkownik nie mógł wymusić ponownej autoryzacji connectora w ChatGPT.

## Ryzyko

- `Origin: null` jest akceptowane **tylko** tam, gdzie żądanie ma token CSRF podpisany kluczem sesji (`hmac('mcp-connected:' + sessionId)`); obcy `Origin` nadal daje `403 bad_origin`, zły CSRF nadal `403`. Pozostałe mutacje `alphavault.pl` i MCP zachowują dotychczasową regułę (odrzucają `null`).
- `Referrer-Policy` na MCP zmienia się na wartość używaną już przez `alphavault.pl` (`strict-origin-when-cross-origin`); nagłówki bezpieczeństwa `nosniff` i `X-Frame-Options: DENY` bez zmian.
- Rollback: revert PR + ponowny deploy MCP (`deploy-mcp.yml`, `ref=main`). Brak zmian danych i sekretów.
